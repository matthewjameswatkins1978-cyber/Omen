# Omen 0.9 Performance Baseline

## 0.9-B.1 closeout

This is a measurement record for Preview 5. It is not an optimisation plan
implemented in the runtime. The machine contract remains `0.8`.

- Toolchain: rust-analyzer/rustc `1.98.1` (`48a229ce`), Cargo `1.98.1`,
  active toolchain `1.98.1-x86_64-pc-windows-msvc`, target

## Measured costs

| Operation | Samples | p50 | p95 | Interpretation |
|---|---:|---:|---:|---|
| Cold semantic search | 3 | 8,562 ms | 8,562 ms | End-to-end Omen MCP session, provider startup and first query combined |
| Warm semantic search | 3 | 2 ms | 2 ms | Same MCP session/provider, equivalent query |
| Omen startup/discovery | 3 each | 14–17 ms | 14–19 ms | Fresh Omen process, machine JSON |

The execution difference is not classified as waste. It includes Omen's
execution identity, containment, history/evidence handling, and output
capture.

## Cold semantic breakdown

Omen does not currently expose independently timestamped lifecycle events for
these boundaries. The following is therefore deliberately conservative:

| Stage | Time | Confidence |
|---|---:|---|
| Workspace/resource resolution | UNKNOWN / COMBINED | No public event boundary |
| Provider spawn | UNKNOWN / COMBINED | Process topology proves provider existence, not exact spawn duration |
| Initialize request/response | UNKNOWN / COMBINED | LSP exchange is internal |
| Project/VFS load | UNKNOWN / COMBINED | Included in provider readiness interval |
| Proc-macros/build scripts | UNKNOWN / COMBINED | No Omen-correlated boundary; proc-macro was not consistently visible in snapshots |
| Cache priming | ~5,645–5,670 ms standalone batch phase | Medium; separate rust-analyzer process, not subtraction from Omen total |
| Semantic query | UNKNOWN / COMBINED | First query shares the cold readiness path |
| Omen projection/client response | UNKNOWN / COMBINED | No independent telemetry |

Standalone rust-analyzer `prime-caches` was 5,662 ms; disabling build scripts
was 5,670 ms and disabling proc macros was 5,645 ms on the already-warmed
workspace. These runs identify a substantial provider/project-model phase but
do not prove the first cold Omen breakdown.

## Cache and project discovery audit

- TARGET CACHE: **stable**. Cargo reports `D:\Omen Shell\target` and no
  `CARGO_TARGET_DIR` override was present.
- DUPLICATED BUILD CACHE: **unknown**. No session-specific target directory
  was found, but this audit did not inventory every Cargo or proc-macro cache
  artifact.
- AUTO DISCOVERY CURRENTLY USED: **yes**. The adapter accepts the workspace
  root when it contains `Cargo.toml` or `rust-project.json`; no explicit
  `linkedProjects` configuration is supplied.
- MEASURABLE DISCOVERY COST: **unknown / combined**.
- EXPLICIT PROJECT CANDIDATE: **worth testing post-1.0**, subject to an
  equivalent correctness and freshness proof.

## Cost classification

- ESSENTIAL COST: Omen process launch, containment, execution identity, and
  evidence capture on the execution path.
- AMPLIFIED COST: separate MCP sessions create separate semantic providers;
  this is confirmed, but sharing is not automatically correct.
- UNKNOWN: exact cold semantic stage allocation, proc-macro/build-script
  contribution, agent payload repetition, and complete per-process memory
  attribution.
- POST-1.0 OPTIMISATION CANDIDATES: canonical-workspace provider lifetime or
  multiplexing, explicit project configuration, intent-triggered prewarming,
  stable project-model reuse, and provider tuning. Each requires dedicated
  correctness, freshness, isolation, and performance bats before adoption.

No safe pre-1.0 runtime fix is supported by this evidence. No startup cost was
disabled or moved to the first query.
