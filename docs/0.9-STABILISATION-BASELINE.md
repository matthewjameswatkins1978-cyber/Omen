This document marks the boundary between Omen 0.8 adversarial architecture work and 0.9 product stabilisation.

> **Stop inventing Omen and make Omen boringly dependable.**

> **OMEN SURVIVED THE TERROR BATS.**

There is no Bat 8 and no Terror Bat 8. The adversarial programme is complete; its lessons remain regression coverage.

## What 0.9 is

Omen 0.8 established that the architecture can survive hostile execution, semantic, authority, concurrency, and recovery conditions. Omen 0.9 is the stabilisation phase: freeze the useful contracts, remove ambiguity, measure before optimising, and make the proven machinery dependable for ordinary human and agent workflows.

The 0.9 runtime remains Omen 0.8 Preview 8 until the first intentional 0.9 executable change. Do not create a stable `v0.8.0` release or casually bump the runtime during this documentation-only bootstrap.

## Contract surface

Treat these as frozen or near-frozen unless evidence requires a deliberate compatibility decision:

- Machine Contract, schemas, statuses, Facts, Actions, Evidence, resource identities, and error vocabulary.
- Execution semantics, containment truth, semantic truth states, provider/readiness failures, and MCP projections.
- Omen’s boundary: execution mechanics, machine truth, typed resources, artifacts, and evidence.
- Neighbor boundaries: Tethers controls authority; Lantern owns memory and provenance; Resolve coordinates; ThreadMoth performs bounded structural mutation.

0.9 may clarify or stabilise contracts. It must not weaken authority, turn unsupported or unavailable states into false success, or absorb a neighbouring project’s responsibility.

## Known measured watch items

### Semantic startup

The accepted evidence records:

- Preview 7 final Bat 7 baseline: approximately p50 `4.37s`.
- Preview 8 post-fix installed sessions: p50 `5.94s`, maximum `6.02s`.

Correctness is intact. Treat the difference as a performance investigation candidate. Measure provider startup, workspace discovery, coverage detection, process lifecycle, cache initialisation, and MCP session startup before changing architecture.

### Provider multiplication

Separate MCP sessions may start separate semantic providers. This is not currently a correctness failure. Measure startup cost, memory, multi-session workload, and lifecycle behaviour before considering reuse or multiplexing. Avoid introducing cross-session leakage, stale-provider bugs, daemon fragility, or lifecycle complexity without evidence.

## Human UX gaps

Stabilise the human shell around a restrained prompt and presence model:

```text
~/Projects/Omen  main ✓
\\O/ ›
```

Priorities include startup messaging, deterministic local epigraphs, visible appearance selection, live theme preview, Escape restoration, and four presentation-only themes: Omen, Phosphor, Amber, and Ice. The sigil is human presentation, never machine authority.

## Agent UX gaps

Polish and freeze progressive discovery through:

```text
omen orient --machine
omen capabilities --machine
omen describe ...
omen how ...
omen context --machine
omen action ...
```

Measure calls, bytes, redundant discovery, payload size, progressive loading, and caching. Agents should receive enough deterministic contract truth for the current job without being taught Omen externally.

## Packaging gaps

Make installation uneventful and repeatable: install, upgrade, rollback, uninstall, PATH handling, version identity, release provenance, and the preview-to-stable transition. Preserve the exact-artifact discipline already demonstrated by the Preview Conveyor.

## Cross-platform gaps

Use evidence from Windows, Linux, macOS, WSL, PowerShell, Nushell, and Bash. Keep ordinary cross-platform tests shell-independent. Platform-specific code is justified where the platform itself supplies the capability, such as Windows Job Objects.

## Companion-language plan

Omen is not a programming or glue language. It connects languages while preserving one semantic authority model.

- Bash: compatibility, Unix/Linux scripts, CI, and SSH.
- Nushell: structured-shell reference integration.
- Python: programmable automation bridge.
- PowerShell: Windows, administration, and object-pipeline integration.

Begin with thin, high-quality reference integrations and clean contracts. Do not build four large ecosystems before 1.0.

## 0.9 workstreams

The proposed bounded order is:

1. Contract freeze and inventory.
2. Performance baseline and measured harness-tax investigation.
3. Human shell, prompt, appearance, and setup.
4. Agent discoverability and payload polish.
5. Bash, Nushell, Python, and PowerShell integration surfaces.
6. Cross-platform hardening.
7. Packaging, update, rollback, and uninstall.
8. Documentation and real-workflow validation.
9. Release candidate preparation.

The order may change only when dependency evidence justifies it. Each workstream should be small, observable, and independently verifiable.

## Explicit non-goals

0.9 is not another architectural invention cycle. It explicitly does not include:

- a new architectural universe or giant aesthetic refactor;
- new Bat or Terror Bat families;
- an Omen programming language;
- provider-specific semantic authority in Omen core;
- authority migration from Tethers;
- memory migration from Lantern;
- coordination migration from Resolve;
- mutation or structural-authority migration from ThreadMoth;
- speculative provider sharing before measurement;
- a stable `v0.8.0` release created only to mark the milestone.

## First decision point

Before substantial implementation, choose the first bounded 0.9 packet from the workstream order. The recommended starting point is **0.9-A: contract freeze and inventory**, because every later stabilisation stream depends on knowing which fields, statuses, identities, and error states are deliberate public contract.
